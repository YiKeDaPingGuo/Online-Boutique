# 数据集说明

## 概述

本数据集来源于对微服务系统 **Online-Boutique**（部署于本地 Minikube 集群）的 Prometheus 监控数据导出，服务于大作业阶段四的论文算法复现。数据分为两部分：

| 数据源 | 数据内容 | 时间段 | 采样间隔 |
|--------|---------|--------|---------|
| **oversee_24h** | oversee 微服务应用层指标 | 06-08 23:34 ~ 06-09 13:08（约 13.6 小时） | 15s |
| **cluster_24h** | Minikube 集群节点 / Pod 级指标 | 06-08 13:08 ~ 06-09 13:08（24h 跨度，有效约 8.8h） | 30s |

> **说明：** oversee 数据未能覆盖完整 24h，因为电脑中途没电关机导致 `oversee` Pod 和 default Prometheus 重启，仅保留关机前约 13.6 小时数据。cluster 数据虽有 24h 跨度，但因睡眠/关机存在累计约 15.2 小时的数据空隙。

## CSV 文件格式说明

所有文件均采用统一的格式：

### 通用列

| 列名 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `timestamp` | int | Unix 时间戳（秒） | `1780911783` |
| `datetime` | string | 北京时间（Asia/Shanghai, UTC+8） | `2026-06-08 23:52:33` |
| `metric` | string | Prometheus 指标名 | `online_boutique_request_latency` |
| `value` | float | 指标数值 | `15.0` |
| `label_*` | string | Prometheus 标签维度（详见各文件） | `label_service: adservice` |

### Label 列说明

各文件的 label 列因数据源不同而有所差异：

- **oversee 指标**：`label_application`, `label_instance`, `label_job`, `label_service`（含按微服务名拆分的维度）
- **HTTP 指标**：额外包含 `label_method`（GET/POST）、`label_uri`、`label_status`（HTTP 状态码）、`label_outcome`、`label_exception`
- **JVM 指标**：额外包含 `label_area`（heap/non-heap）、`label_id`（内存池名）
- **GC 指标**：额外包含 `label_action`、`label_cause`（GC 原因）
- **磁盘指标**：额外包含 `label_path`（磁盘路径）
- **节点指标**：`label_instance`（节点 IP:端口）、`label_job`（exporter 类型）
- **节点 CPU**：额外包含 `label_cpu`（CPU 编号）、`label_mode`（user/system/idle/iowait 等）
- **节点磁盘**：额外包含 `label_device`、`label_fstype`、`label_mountpoint`
- **节点网络**：额外包含 `label_device`（网卡名）
- **容器指标**：包含 `label_pod`、`label_container`、`label_namespace`、`label_node` 等。尤其是 `label_pod` 可以用来按 Pod 维度聚合分析

## 故障注入信息

数据集中包含 ChaosMesh 故障注入期间采集的异常数据，适合用于异常检测算法验证。

### 注入的故障类型

| 故障类型 | 目标服务 | 注入时间 | 说明 |
|---------|---------|---------|------|
| CPU 压力 80% | `productcatalogservice` | 21:39 左右（一次性） | CPU 突增最高达正常值的 **36 倍** |
| CPU 压力 90% | `recommendationservice` | 每 15 分钟定时（21:39~23:24 共约 6 轮） | 周期性 CPU 峰值 |
| 内存压力 256MB | `recommendationservice` | 21:39 左右 | 内存占用突增 |
| 网络延迟 200ms | `frontend` | 21:35 左右 | 前端响应变慢 |
| 网络延迟 300ms | `frontend` | 每 10 分钟定时 | 周期性延迟 |
| 30% 丢包 | `frontend` | 一次性 | 请求丢失 |
| Pod 随机杀死 | `default` 命名空间 | 每 5 分钟定时 | Pod 重启 |

### 数据中可观测的异常特征

- **`container_cpu_usage_seconds_total`** — productcatalogservice 和 recommendationservice 出现周期性 CPU 峰值（21:39 起每 15 分钟一次）
- **`container_memory_working_set_bytes`** — 容器重启时内存归零，出现断点
- **`node_load1` / `node_procs_running`** — CPU 压力期间的节点负载变化
- **`node_network_receive_bytes_total`** / **`node_network_transmit_bytes_total`** — 网络延迟/丢包期间流量模式变化
- **`online_boutique_request_latency`** — 故障期间的请求延迟变化（oversee 数据）
- **`online_boutique_errors_total`** — 故障期间的错误计数变化

## 注意事项

1. **时间戳：** 所有 `datetime` 字段均为 **北京时间（Asia/Shanghai, UTC+8）**，`timestamp` 字段为标准 Unix 时间戳（UTC）
2. **数据空隙：** cluster 数据存在 5 段空隙（累计约 15.2 小时），原因为电脑进入睡眠状态以及中途没电关机导致 Minikube VM 暂停。具体空隙时间段：13:56~16:48（睡眠）、16:53~17:23（睡眠）、00:53~01:10（短时）、01:14~03:24（关机）、03:29~12:49（关机）。oversee 数据也存在对应的关机空隙。
3. **oversee 数据范围：** oversee 数据约 13.6 小时（06-08 23:34 ~ 06-09 13:08），未能覆盖完整 24h。原因有两方面：一是 `oversee` Pod 被 ChaosMesh 的 Pod 杀死实验误杀导致重启；二是电脑没电关机导致 default Prometheus 丢失关机期间的数据。
4. **指标单位：** 所有 byte 类指标均以 **字节（bytes）** 为单位，CPU 使用率为 0~1 之间的浮点数，延迟指标单位为秒（seconds）
5. **性能开销：** 导出脚本通过 Prometheus HTTP API 查询，导出 112M 的 `cluster_pod_resources.csv` 耗时较长，建议结合 `step` 参数控制数据粒度
6. **重复导出：** 如需重新导出，先执行 `kubectl port-forward` 端口转发，再运行 `python tests/export_prometheus_data.py`

## 使用方法

### Python 读取示例

```python
import pandas as pd

# 读取 oversee 请求指标
df = pd.read_csv('exported_data_all/oversee_24h_oversee_requests.csv')
df['timestamp'] = pd.to_datetime(df['timestamp'], unit='s', utc=True)
df = df.pivot_table(index='timestamp', columns='metric', values='value')

# 读取容器 CPU/内存
df_pod = pd.read_csv('exported_data_all/cluster_24h_cluster_pod_resources.csv')
# 按 Pod 过滤
df_frontend = df_pod[df_pod['label_pod'].str.contains('frontend', case=False)]
```

### 关联分析思路

- **应用层 vs 基础设施层：** 将 oversee 的请求延迟/错误率与 cluster 的容器 CPU/内存做时间对齐，观察故障从基础设施到应用层的传导
- **正常 vs 异常对比：** 使用故障注入前（13:08~13:56）的数据作为基线，与故障注入期间（21:39~23:34）的数据进行对比。注意 oversee 数据仅覆盖 23:34 之后，因此 oversee 指标需在 oversee 数据范围内对比。
- **周期性异常：** recommendationservice 每 15 分钟的 CPU 峰值可用于检测周期性异常模式
